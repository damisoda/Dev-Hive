# Jira 가이드

본 문서는 Jira를 처음 사용하는 팀원을 위한 가이드이다. 본 프로젝트는 Jira의 Kanban 보드 방식을 사용하며, Epic 단위로 Layer를 관리한다.

---

## 1. Jira 기본 용어

| 용어 | 의미 |
|------|------|
| 프로젝트(Project) | 작업 단위의 최상위 묶음. 본 프로젝트는 `Dev-Hive`이며 키는 `HIVE`이다. |
| 이슈(Issue) | 작업의 최소 단위. "카드"라고도 부른다. |
| Epic | 여러 이슈를 묶는 큰 단위. 본 프로젝트에서는 Layer와 1:1 매핑된다. |
| Story | 사용자 가치 단위의 기능 이슈. |
| Task | 기술적 작업 단위 이슈. |
| Bug | 결함 보고 이슈. |
| Component | 영역별 태깅 (Backend, Frontend, AI/ML 등). |
| Label | 자유로운 태그. demo-critical, blocker 등. |
| Assignee | 해당 이슈의 담당자. |
| Reporter | 이슈를 등록한 사람. |
| 보드(Board) | 이슈를 컬럼별로 시각화한 화면. |

---

## 2. 이슈 만들기

작업을 시작하기 전 반드시 Jira에서 이슈를 먼저 만든다. **이슈 없이 시작하는 작업은 컨벤션 위반이다.**

### 생성 절차

1. Jira 좌측 사이드바에서 `Dev-Hive` 프로젝트 진입
2. 우측 상단 **Create** 또는 **만들기** 클릭
3. 다음 필드를 입력한다.

| 필드 | 내용 |
|------|------|
| Project | `Dev-Hive` (자동 선택됨) |
| Issue type | Story 또는 Task (구분이 모호하면 Task) |
| Summary | 짧고 명확한 제목. 예: "Reddit PRAW 크롤러 PoC" |
| Description | 작업 내용, 인수 조건, 참고 링크 등 |
| Epic | 해당 Layer Epic 연결 |
| Assignee | 본인 (시작 시점에 지정) |
| Component | Backend / Frontend / AI/ML / Data / DevOps / Docs 중 1개 |
| Label | 필요 시 demo-critical, learning 등 |

4. **Create** 클릭

생성된 이슈는 키(예: `HIVE-12`)를 받는다. 이 키를 브랜치명·커밋·PR에 사용한다.

---

## 3. 이슈 타입 구분

| 타입 | 용도 | 예시 |
|------|------|------|
| Epic | 큰 묶음 (본 프로젝트에서는 Layer) | "Layer 1 — Walking Skeleton" |
| Story | 사용자 가치 단위 기능 | "유저가 자가평가를 통해 첫 추천을 받을 수 있다" |
| Task | 기술 작업 단위 | "pgvector 확장 설치" |
| Bug | 결함 보고 | "추천 API가 401 반환하는 회귀 발생" |

본 프로젝트는 학생 규모이므로 대부분 Task로 운영해도 무방하다. Story와 Task의 엄밀한 구분에 시간을 쓰지 않는다.

---

## 4. 카드 상태 흐름

```
Backlog → To Do → In Progress → In Review → Done
```

| 컬럼 | 의미 | 진입 조건 |
|------|------|---------|
| Backlog | 우선순위 미정 또는 미래 작업 | 이슈 생성 직후 기본 상태 |
| To Do | 이번 주에 작업 예정, 우선순위 결정됨 | 주간 동기화에서 끌어올림 |
| In Progress | 작업 중 | 본인이 작업 시작 시 직접 이동 |
| In Review | PR 올라가 리뷰 대기 | PR 생성 시 자동 이동 (Automation) |
| Done | 머지 완료 | PR 머지 시 자동 이동 (`Closes` 키워드) |

### 상태 이동 방법

- 보드 화면에서 카드를 드래그하여 다음 컬럼으로 이동
- 또는 Smart Commits로 자동 전환 (`Jira-GitHub 연동 가이드` 참조)
- 또는 카드 상세 화면 우측 상단 상태 버튼 클릭

---

## 5. Assignee 지정

- 작업을 시작할 때 반드시 본인을 Assignee로 지정한다.
- 한 이슈에 Assignee는 한 명만 둔다 (협업이 필요한 경우 댓글에서 멘션).
- 작업이 중단될 경우 Assignee를 해제하고 카드를 Backlog로 옮긴다.

---

## 6. Component 사용

본 프로젝트의 Component 목록이다. 이슈 생성 시 1개를 반드시 선택한다.

| Component | 책임 영역 |
|-----------|---------|
| Backend | FastAPI 서버, DB 모델, 인증 |
| Frontend | Next.js, UI 컴포넌트 |
| AI/ML | 태깅, 임베딩, GraphSAGE, GraphRAG |
| Data | 크롤러, 데이터 정규화 |
| DevOps | 배포, CI/CD, 인프라 |
| Docs | 문서, 발표 자료 |

Component는 보드 필터링에 활용된다. 예: "AI/ML 영역 In Progress만 보기".

---

## 7. Label 사용

본 프로젝트에서 권장하는 라벨이다. 여러 개 동시에 부여할 수 있다.

| Label | 의미 |
|-------|------|
| `demo-critical` | 데모 시연에 필수인 작업. 우선순위 최상위. |
| `blocker` | 다른 작업을 막고 있음. 즉시 처리 필요. |
| `learning` | 학습/조사가 필요한 작업. 시간 추정 어려움. |
| `refactor` | 기존 코드 개선. 기능 추가 아님. |
| `tech-debt` | 임시 처리 후 나중에 정리 필요. |

---

## 8. 댓글 사용

이슈 카드의 댓글은 작업 진행 상황을 기록하는 핵심 수단이다.

- 작업 중 발견한 이슈나 결정 사항은 카드 댓글에 남긴다.
- 다른 사람의 답변이 필요하면 `@이름` 형식으로 멘션한다. 멘션된 사람에게 알림이 간다.
- 외부 링크(논문, Notion 문서, GitHub PR 등)는 댓글에 첨부한다.
- 작업이 막혔을 때 막힌 이유를 댓글로 남긴다.

---

## 9. 막혔을 때 대응

- 카드에 `blocker` 라벨을 추가한다.
- 댓글에 막힌 이유와 시도한 방법을 명시한다.
- 주간 동기화에서 공유한다. 급한 경우 즉시 팀 채널에서 도움을 요청한다.

---

## 10. 데일리 워크플로우 (권장)

매일 아침 5분만 다음을 수행한다.

1. 본인의 In Progress 카드를 확인한다.
2. 어제 완료한 작업을 Done으로 이동한다 (Smart Commit이 자동 처리하지 않은 경우).
3. 오늘 작업할 다음 카드를 In Progress로 이동한다.
4. 막힌 게 있다면 댓글로 공유하거나 팀 채널에 알린다.

---

## 11. 주간 동기화 활용

매주 일요일 저녁 30분 동기화 미팅에서 다음을 수행한다.

| 시간 | 활동 |
|------|------|
| 0:00 – 0:05 | 지난 주 Done 컬럼 점검. 누가 무엇을 완료했는지 공유. |
| 0:05 – 0:20 | 다음 주 To Do 컬럼 확정. Backlog에서 우선순위 끌어올림. |
| 0:20 – 0:30 | 막힌 항목과 도움 요청 공유. |

데모 직전 주(5/29, 6/5, 6/27)에는 1시간으로 연장하여 데모 리허설을 포함한다.

## 12. 자주 묻는 질문

### Q. 작업이 너무 작은데 카드를 꼭 만들어야 하나?
A. 만든다. 10분짜리 변경이라도 카드가 있어야 추적이 가능하다. 다만 Description은 간략하게 적어도 무방하다.

### Q. 한 이슈가 너무 커지는 것 같다.
A. 1일 이상 걸릴 것 같으면 분할한다. 부모 이슈를 만들고 하위 이슈로 나눈다.

### Q. 이미 만든 PR에 다른 이슈 작업이 섞였다.
A. 새 PR을 만들거나, 새 커밋을 별도 브랜치로 옮긴다. 한 PR은 한 이슈에 대응한다.

### Q. 데모 일정에 영향이 갈 것 같은 작업이다.
A. `demo-critical` 라벨을 붙이고 즉시 팀 채널에 공유한다.
