# Pull Request 가이드

본 문서는 Pull Request(이하 PR)의 작성·리뷰·머지 절차를 정의한다. PR은 본인의 코드를 다른 사람의 검토를 거쳐 공동 코드베이스에 반영하는 가장 기본적인 협업 메커니즘이다.

---

## 1. PR이란

Pull Request의 약자이다. 본인이 작업한 브랜치를 develop 또는 main 브랜치에 합치기 전에 다른 팀원이 검토하도록 요청하는 절차이다.

---

## 2. PR 생성 시점

다음 시점에 PR을 생성한다.

- 해당 이슈의 작업이 완료되어 코드가 정상 작동하는 시점
- 작업이 길어지는 경우, 중간 점검을 위해 Draft PR로 일찍 올려도 무방하다. Draft 상태에서는 머지가 불가하며 미리보기 목적으로 활용된다.

---

## 3. PR 제목 컨벤션

```
[HIVE-12] feat: Reddit PRAW 크롤러 v0 구현
```

- 대괄호 안에 Jira 이슈 키를 적는다.
- 콜론 뒤로 커밋 타입과 짧은 설명을 적는다.
- 타입은 커밋 메시지와 동일한 규칙을 따른다(feat, fix, docs, style, refactor, test, chore).

---

## 4. PR 본문 작성

`.github/PULL_REQUEST_TEMPLATE.md` 파일이 PR 생성 시 자동으로 본문을 채워준다. 본문에는 다음 항목을 반드시 포함한다.

### 필수 항목

| 항목 | 설명 |
|------|------|
| 관련 Jira 이슈 | `Closes HIVE-12` 형식. `Closes` 키워드 사용 시 PR 머지와 함께 이슈가 Done으로 자동 이동한다. |
| 변경 사항 요약 | 무엇이 어떻게 바뀌었는지 3~5줄로 정리한다. |
| 테스트 방법 | 리뷰어가 변경 사항을 어떻게 검증할 수 있는지 구체적으로 적는다. |
| 셀프 체크리스트 | 본 가이드 6절 참조. |

### 선택 항목

| 항목 | 설명 |
|------|------|
| 스크린샷 | UI 변경 시 필수. BE/AI 변경 시 실행 결과 로그를 첨부한다. |
| 추가 컨텍스트 | 리뷰 전에 알아두면 좋을 배경, 결정 사유, 알려진 한계 등. |

---

## 5. PR 작성 예시

```markdown
## 관련 Jira 이슈

Closes HIVE-12

## 변경 사항 요약

- Reddit PRAW를 사용하여 r/ClaudeAI에서 10건의 글을 수집하는 PoC를 구현
- 수집된 글은 raw_contents 테이블에 적재되며, 메타데이터(작성자, 작성일, upvote 수)도 함께 저장
- 환경 변수 REDDIT_CLIENT_ID, REDDIT_CLIENT_SECRET이 필요 (`.env.example`에 추가)

## 테스트 방법

1. `.env`에 Reddit API 자격증명 설정 후
2. `python backend/crawler/reddit_test.py` 실행
3. DB에서 `SELECT COUNT(*) FROM raw_contents WHERE source = 'reddit'` 으로 10건 적재 확인

## 셀프 체크리스트

- [x] 로컬에서 동작 확인 완료
- [x] 다른 모듈 회귀 영향 검토
- [x] .env / 비밀 정보 커밋 여부 확인
- [x] 불필요한 console.log / print 제거
- [x] 코드 컨벤션 준수
```

---

## 6. 셀프 체크리스트

PR을 올리기 전 본인이 확인할 항목이다. 모든 PR에 포함한다.

```
- [ ] 로컬에서 동작 확인 완료
- [ ] 다른 모듈 회귀 영향 검토 (의존하는 코드가 깨지지 않았는가)
- [ ] .env / 비밀 정보 커밋 여부 확인
- [ ] 불필요한 console.log / print 제거
- [ ] 코드 컨벤션 준수 (ESLint, Black, Prettier 등)
- [ ] 관련 Jira 이슈 키를 PR 제목과 본문에 포함
```

---

## 7. 리뷰어 지정

- 해당 영역(Backend, Frontend, AI/ML 등) 담당자 한 명 이상을 reviewer로 지정한다.
- 영역이 모호하면 팀 채널(Discord 또는 카카오톡)에서 알린다.
- 본인이 충분히 검토한 코드라도 다른 사람의 검토를 받는 것이 원칙이다.

---

## 8. 머지 전 조건

다음 조건을 모두 충족한 뒤 머지한다.

- 리뷰어 1명 이상의 Approve
- 댓글로 요청된 변경 사항을 모두 반영
- 충돌이 없음 (있을 경우 작성자가 해결)
- CI(자동 빌드/테스트)가 있다면 통과. 없다면 본인 책임 하에 동작 확인.

---

## 9. 머지 방식

GitHub의 머지 옵션 중 **Squash and merge**를 사용한다.

이유:
- feature 브랜치의 여러 WIP 커밋이 develop 히스토리에 하나의 깔끔한 커밋으로 합쳐진다.
- develop 히스토리가 선형적이고 읽기 쉬워진다.
- 되돌릴 때 한 커밋만 revert하면 된다.

머지 후에는 feature 브랜치를 삭제한다. GitHub UI에서 "Delete branch" 버튼을 누르거나, 로컬에서 다음 명령어를 사용한다.

```bash
git checkout develop
git pull origin develop
git branch -d feature/HIVE-12-reddit-crawler
```

## 10. PR 크기 가이드

| 변경 라인 수 | 평가 |
|-----------|------|
| ~ 100줄 | 이상적, 리뷰 빠름 |
| 100 ~ 500줄 | 정상적인 크기 |
| 500줄 ~ | 분할 고려 |
| 1000줄 ~ | 분할 필수 |

변경 파일 수가 30개를 넘는 경우, 다음 PR로 미루거나 작업을 나눈다. 큰 PR은 리뷰어에게 부담을 주고 결함을 놓치게 만든다.

---

## 11. 리뷰어 입장의 가이드

리뷰어 역할을 맡은 사람을 위한 지침이다.

- PR 등록 후 24시간 이내에 리뷰를 시도한다.
- 코드 변경의 "무엇"이 아니라 "왜"를 본다. 왜 이렇게 짰는지 이해 후 평가한다.
- 칭찬할 부분은 칭찬, 개선할 부분은 구체적으로 지적한다. 모호한 "이상하다"는 피한다.
- `LGTM`(Looks Good To Me)은 Approve와 동일한 의미로 사용된다.
- 리뷰 댓글의 종류:
  - **Comment**: 의견 공유, 머지 가능
  - **Request changes**: 변경 필요, 머지 불가
  - **Approve**: 머지 OK

---

## 12. 자주 발생하는 상황 대처

### 리뷰 요청 후 한참 답이 없는 경우
1. 24시간 후 팀 채널에서 리마인드한다.
2. 그래도 응답이 없으면 다른 팀원에게 추가 리뷰를 요청한다.

### 리뷰 받은 후 큰 폭의 수정이 필요한 경우
1. Draft PR로 전환한다.
2. 수정 후 다시 Ready for review로 전환한다.

### 본인의 PR에 충돌이 생긴 경우
1. `GitHub 협업 가이드` 7절의 충돌 해결 절차를 따른다.
2. 해결이 어려우면 머지하지 않고 팀에 공유한다.
